## data-modeling — grade C+

Strong schema design (A- alone) dragged to C+ by verified migration drift (P0). Findings below are the five action-critical issues; see each detail for the fix.

### Findings

- **[P0] Migrations drifted from schema; CI auto-applies then deploys code querying non-existent tables**
  - All 5 committed migration .sql (newest 20260529164110_confidence_engine_p0) have ZERO refs to Outcome/ProviderKey/ResumeProfile/disfluencyJson/keySource/rubricVersion; schema.prisma declares them live. deploy.yml:66 runs prisma migrate deploy, :67 migrate status (diffs DB vs committed migrations only, NOT vs schema.prisma), deploy needs:migrate. A clean prod/DR rebuild yields a DB missing those tables; CI green; every BYOK/outcome/resume/disfluency query throws. They exist only via dev-only db:push.
  - ref: `prisma/migrations/20260529164110_confidence_engine_p0/migration.sql:65 and .github/workflows/deploy.yml:66`
  - why it matters: The un-migrated features are the moat (BYOK, A1 outcome, resume, disfluency); a DR/staging rebuild breaks the core flow while CI is green.
  - fix: prisma migrate dev to commit the missing migration (3 tables+3 enums, disfluencyJson/keySource, apiKey FK). Add CI gate prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --exit-code.
  - alternatives: db push (no rollback/unauditable) and migrate resolve (tables truly absent) rejected; the diff gate is the cheapest guard.

- **[P1] MockSession.apiKeyId is a bare FK-less column; schema declares a real relation**
  - migration.sql:65 created apiKeyId TEXT with no REFERENCES/SET NULL. schema.prisma:253 declares apiKey ProviderKey @relation(onDelete: SetNull). Any migrated DB has free-text apiKeyId, zero referential integrity, pointing at a non-existent table.
  - ref: `prisma/schema.prisma:252-253`
  - why it matters: Deleted/rotated keys leave dangling apiKeyId; cost-attribution joins return orphans; SetNull never fires; the relation graph misleads readers.
  - fix: Ensure the catch-up migration's generated SQL has ADD CONSTRAINT FK (apiKeyId) REFERENCES ProviderKey(id) ON DELETE SET NULL on the existing column.
  - alternatives: A loose pointer is rejected; the design wants SetNull cost-attribution and code resolves which key paid.

- **[P1] Outcome.rubricVersion never written; judgeModel on wrong table; A1 labels cannot survive rubric churn**
  - Outcome.rubricVersion (schema:411) is NEVER assigned (grep src+packages); outcome/route.ts:56-66 snapshots only predictedSignal/predictedWeakest. judgeModel hardcoded gpt-4o-mini on MockSession (sessions/route.ts:142), not PanelVerdict (schema:333-345, has neither). Rubric versionless (coach-core 0.1.0), so a rubric edit silently re-bases all prior DimensionScore/Outcome rows.
  - ref: `prisma/schema.prisma:411 and src/app/api/mock/sessions/route.ts:142`
  - why it matters: A prediction label is only valid relative to its rubric+judge; unstamped, the A1 moat corpus degrades to noise as the rubric evolves; predictions are immutable so this is unrecoverable.
  - fix: Add a REACT_JS_RUBRIC_VERSION constant; stamp rubricVersion+judgeModel on PanelVerdict at judgment, snapshot into Outcome at capture; add columns in the catch-up migration.
  - alternatives: package.json/Git-SHA not per-row/too coarse; deferring is fatal for the snapshot. A string constant is the cheapest fix.

- **[P2] Fluency-metric join relies on a non-unique index; a reused clientTurnId writes metrics to multiple turns**
  - MockTurn has only @@index([sessionId, clientTurnId]) (schema:312, non-unique). turns/audio/route.ts:117-126 uses updateMany on (sessionId, clientTurnId, role:USER), checks only res.count===0 never count<=1. PracticeTurn correctly has @@unique([sessionId, clientTurnId]) (132); seq-uniqueness does not cover this. A reused clientTurnId fans one answer's metrics onto multiple USER turns; the judge aggregates contaminated composure/fluency.
  - ref: `src/app/api/mock/sessions/[id]/turns/audio/route.ts:117-126`
  - why it matters: Disfluency/composure is the differentiator; silent fan-out (updateMany never fails) corrupts the rollup feeding the score/report and defeats retry-idempotency.
  - fix: Add @@unique([sessionId, clientTurnId]) (nullable keeps NULL interviewer turns distinct); switch to update on the unique key or assert count<=1. Fold into the catch-up migration.
  - alternatives: Join on seq impossible: seq is assigned async at dequeue after the upload races ahead; clientTurnId exists to bridge that gap.

- **[P2] Money refund arithmetic leaves Postgres Decimal for JS float before the GREATEST update**
  - estUsd/reservedUsd/settledUsd are Decimal (schema:490,496-497). The daily-cap reserve correctly stays in SQL (spend.ts:46-49, no TOCTOU). But settle: refund = Math.max(0, Number(r.reservedUsd) - settledUsd) (line 72), then GREATEST(estUsd - refund, 0) (78-82). Decimal to float to Decimal, so sub-cent drift accumulates in GlobalSpend.
  - ref: `src/lib/mock/spend.ts:72-82`
  - why it matters: GlobalSpend is the daily kill-switch; float drift makes the cap off by fractions of a cent and the meter non-auditable.
  - fix: Keep the subtraction in SQL/Decimal: GREATEST(estUsd - (reservedUsd::decimal - settledUsd::decimal), 0), or use Prisma.Decimal end to end.
  - alternatives: Integer-cents re-type is cleaner but a bigger migration; the surgical SQL/Decimal fix preserves the design at near-zero risk.

## architecture-boundaries — grade B

The BFF -> orchestrator -> pure-package layering is real and disciplined: `@sevenlabs/coach-core` has zero I/O (verified by grep across all 13 files), all DB access funnels through `src/lib/db.ts`, all OpenAI/Deepgram I/O sits behind `src/lib/coach/*` wrappers, and routes are thin auth+validate adapters. That three-layer spine holds. The architectural debt is NOT layering — it is naming and ownership. The interview-panel product (the strategic bet, per MEMORY) is physically filed under `coach`-named modules: it imports `mintRealtimeEphemeral`/`judgeCommittee`/`scoreAgainstRubric` from `src/lib/coach/openai.ts`, `transcribeVerbatim` from `src/lib/coach/deepgram.ts`, and 9 of 13 `coach-core` modules are panel-only logic (disfluency, panel-composition, panel-context, seat-openers, resume, realtime-cost, interviewer-guardrails, question-bank, + the verbatim path). The `coach-core` name now covers two products with only ~3 coach-specific modules. On the convergence question: the two products ALREADY share a spine in fact (one OpenAI boundary, one rubric/SignalLevel contract, one `PracticeTurnRole` enum reused by both `PracticeTurn` and `MockTurn`), but it is an accidental, mis-labeled spine rather than a designed one — and the two turn DATA models are forked (`PracticeTurn` vs `MockTurn` carry near-identical role/transcript/metricsJson/clientTurnId fields with no shared abstraction). The right move is NOT to merge the two products' runtimes (they have fundamentally different transports: synchronous Whisper batch vs WebRTC Realtime) but to (a) rename the shared spine to reflect that it serves both, (b) make the leaky shared boundary explicit (a `src/lib/llm/` or `src/lib/providers/` for the OpenAI/Deepgram clients, out of `coach/`), and (c) decide whether the turn model converges. The boundary leaks are all the convention-only kind (magic strings, duplicated config, untyped Json blobs) that the type system does not see.

### Findings

- **[P1] The shared spine is real but mis-named: the panel product depends on `coach`-named modules across the board**
  - Verified by grep. The interview-panel product imports from `src/lib/coach/openai.ts` in SEVEN places that are NOT the coach product: `src/app/api/mock/sessions/route.ts:8` and `mint/route.ts:8` (mintRealtimeEphemeral, ProviderError), `src/app/api/resume/route.ts:12` (extractResumeJson), `src/app/api/mock/sessions/[id]/turns/audio/route.ts:7` (transcribeAudio), `src/app/api/keys/route.ts:8` (ProviderError), `src/lib/byok.ts:3` (mintRealtimeEphemeral), `src/lib/mock/panel-orchestrator.ts:31` (scoreAgainstRubric, judgeCommittee). Separately, `src/lib/coach/deepgram.ts` is consumed ONLY by the panel audio route (`turns/audio/route.ts:8`) yet lives in `src/lib/coach/` and imports `ProviderError` back from `src/lib/coach/openai.ts` — a file in the coach folder serving only the panel. And `@sevenlabs/coach-core/src/index.ts` (read in full) re-exports the ENTIRE panel domain: disfluency, panel-composition (buildSeatRubric/finalizeVerdict/computeComposure), panel-context, seat-openers, resume, realtime-cost, interviewer-guardrails, question-bank — only `speech-analysis`, `coach-prompt`, and shared `rubric-definitions`/`redaction` are coach-product code. So `coach-core` is a misnomer: it is the interview-engine pure-logic package with a coach name.
  - ref: `src/lib/coach/openai.ts:217 (mintRealtimeEphemeral — panel); src/lib/coach/deepgram.ts:26 (panel-only, in coach folder); packages/coach-core/src/index.ts:36-91 (panel exports under coach name)`
  - why it matters: This is the #1 readability/maintainability tax on the strategic product. A new contributor (or future-self) reading the repo's entry docs sees the panel — the actual bet per MEMORY — scattered under a legacy `coach` namespace, with no signal that `src/lib/coach/openai.ts` is the shared LLM boundary for both products and `src/lib/coach/deepgram.ts` is panel-only. It directly obscures the most important subsystem. It also makes the dependency graph misleading: a `grep coach` undercounts the panel's surface, and the panel's most load-bearing files (mint, judge) read as coach add-ons.
  - fix: Rename to reflect the shared reality. Move the cross-product LLM clients out of `src/lib/coach/` into a neutral `src/lib/llm/` (or `src/lib/providers/`): `openai.ts` (the single OpenAI boundary), `deepgram.ts`. Keep coach-only orchestration (`turn-orchestrator.ts`, `aggregates.ts`) in `src/lib/coach/`. Rename the `@sevenlabs/coach-core` package to `@sevenlabs/interview-core` (or split — see alternatives), since 70% of it is panel logic. Update the three Vitest aliases and the barrel. This is mechanical (imports + package.json + vitest.config.ts) and has no runtime risk — it is pure relabeling to make the boundary match reality.
  - alternatives: (1) Leave it — rejected: the misnomer is precisely the thing that makes the strategic product hard to read, and the cost to rename is near-zero. (2) Split coach-core into `coach-core` + `panel-core` — viable and cleaner long-term, but it FORCES a decision on the genuinely-shared modules (`rubric-definitions.ts` is used by BOTH; `redaction.ts` is cross-cutting), which would need a third `shared` package; given the single-process monorepo and that the packages ship as raw TS source with no build step, a 3-way split is more ceremony than this stage warrants. The rename + folder move captures 80% of the value at 20% of the churn. (3) Merge the two products' runtimes onto one engine — rejected, see the dedicated convergence finding.

- **[P1] Two forked turn data-models (`PracticeTurn` vs `MockTurn`) with no shared abstraction — the convergence decision the codebase is dodging**
  - Both turn tables (schema.prisma:117-134 and :288-312) carry near-identical columns: `role PracticeTurnRole`, `transcript`, `metricsJson Json?`, `clientTurnId String?`, `createdAt`. `MockTurn` adds panel-specific fields (`seq`, `seatId`, `disfluencyJson`, `events`, `audioStartMs/EndMs`, `transcriptionMissing`). The schema explicitly REUSES the coach enum: `MockTurn.role PracticeTurnRole` with the comment 'role=COACH means interviewer seat' (schema.prisma:139,293). So the data layer already half-shares (one role enum) but forks the table. The `metricsJson` concept is duplicated: coach writes `speechMetrics` (WPM/pauses/fillers from Whisper), panel writes the same SHAPE plus a separate `disfluencyJson` from Deepgram. There is no shared 'Turn' or 'SpeechMetrics' abstraction at the storage boundary — `speechMetricsSchema` from shared-types is the only thing bridging them, and it is validated independently in each product's read path.
  - ref: `prisma/schema.prisma:117-134 (PracticeTurn) vs :288-312 (MockTurn); :139,293 (PracticeTurnRole reuse)`
  - why it matters: This is the concrete form of the big convergence question. The duplication is small TODAY (two tables, ~5 overlapping columns) but it is the seam where divergence compounds: any future change to how a 'turn' or its delivery metrics are modeled (e.g. adding the warmup-baseline self-relative delta that MEMORY calls the headline differentiator) has to be applied twice, and the two `metricsJson` blobs can drift in shape with nothing enforcing parity. Reusing `PracticeTurnRole` for `MockTurn` is a latent footgun: COACH meaning 'coach' in one table and 'interviewer seat' in the other is a documented-by-comment overload that a refactor of the enum would silently break across both products.
  - fix: Do NOT merge the tables — the access patterns differ (coach is createdAt-ordered request/response, panel is seq-ordered single-writer queue with idempotency on (sessionId,seq)). Instead: (1) extract a shared `SpeechMetrics`/`Turn-metrics` Zod schema in shared-types that BOTH `PracticeTurn.metricsJson` and `MockTurn.metricsJson` validate against on read AND write (today only panel-orchestrator validates on read; coach casts) — this gives the convergence benefit (one delivery-metrics contract) without coupling the tables. (2) Rename the shared enum to a neutral `TurnRole { USER, ASSISTANT }` (or keep two enums) so the 'COACH means interviewer' overload stops being a comment-enforced trap. The turn STORAGE stays forked; the turn METRICS CONTRACT converges.
  - alternatives: (1) Full table merge into one polymorphic `Turn` with a discriminator column — rejected: the panel's `@@unique([sessionId, seq])` single-writer model and the coach's `@@unique([sessionId, clientTurnId])` createdAt-ordered model are genuinely different invariants; a merged table would need nullable everything and weaker constraints, losing the integrity both currently have. (2) Keep fully forked, do nothing — rejected: leaves the metricsJson shape un-contracted and the enum overload as a trap. (3) The chosen middle path (shared metrics contract, forked storage, de-overloaded enum) keeps each product's integrity constraints while killing the silent-drift risk — the only option that fits the actual divergent access patterns.

- **[P2] Should the two products converge onto one shared 'interview/turn engine' spine? — Argued from the code: NO at the runtime layer, YES at the contract/naming layer**
  - The transports are irreconcilable. Coach (`turn-orchestrator.ts:77-214`) is a synchronous single-request pipeline: multipart upload -> Whisper batch -> analyzeSpeech -> GPT text -> TTS -> S3 -> two Prisma writes, all in one request frame, server in the audio path. Panel (`use-mock-panel.ts` + `realtime-connection.ts` + `panel-orchestrator.ts`) is WebRTC Realtime: browser<->OpenAI direct (server NEVER in the audio path), push-to-talk, ephemeral minting, a 13-phase client FSM, a single-writer seq turn-queue, and OFF-BAND lease-based judgment. These share no control-flow shape. What they DO share is already maximally shared: one OpenAI boundary (`openai.ts`), one rubric definition (`rubric-definitions.ts` used by both via `getRubricForCompany`/`buildRubricUserMessage` — verified: turn-orchestrator.ts:167 AND panel-orchestrator.ts:62), one `SignalLevel`/`rubricScoresSchema` contract (shared-types/schemas.ts, imported by mock-schemas.ts:2), one role enum. A forced 'one turn engine' abstraction over a request/response loop and a WebRTC FSM would be the speculative over-abstraction CLAUDE.md's karpathy rules explicitly forbid.
  - ref: `src/lib/coach/turn-orchestrator.ts:77 (sync loop) vs src/lib/mock/panel-orchestrator.ts:1 + src/features/mock-panel/lib/realtime-connection.ts (WebRTC FSM); shared at rubric-definitions.ts + openai.ts`
  - why it matters: This is the load-bearing architecture decision feeding the long-run design. Getting it wrong in EITHER direction is expensive: merging the runtimes builds a leaky god-abstraction over two transports that don't rhyme; keeping them fully separate re-duplicates the rubric/metrics/SignalLevel logic that is correctly shared today. The code already found the right seam (share the pure logic + LLM boundary + contracts, fork the transport + storage + report pipeline) — it just labeled it as if only the coach exists.
  - fix: Converge the CONTRACT and NAMING spine, keep the RUNTIME forked. Concretely: (a) the shared OpenAI/Deepgram clients, the rubric/SignalLevel/SpeechMetrics Zod contracts, and the pure analysis logic ARE the shared spine — make that explicit (rename per the P1 findings: neutral `src/lib/llm/`, neutral package name, one delivery-metrics contract). (b) Keep `turn-orchestrator.ts` (coach) and the `mock/*` orchestrator+queue (panel) as two separate runtimes — do not introduce a `TurnEngine` interface they both implement. (c) Treat the coach as the legacy sibling: it is in maintenance (session-close gap unfixed, doesn't use Deepgram/disfluency), so invest convergence effort only where the panel needs it. The verification step: after the rename, `grep -r 'lib/coach' src/app/api/mock` should return ZERO (the panel should no longer import from a `coach` path), and a single `SpeechMetrics` schema should be the only metrics validator in both `aggregates.ts` and `panel-orchestrator.ts`.
  - alternatives: (1) Full runtime convergence onto one 'interview/turn engine' — rejected: the synchronous-batch vs WebRTC-realtime transports share no control flow; a unifying interface would be abstraction-for-its-own-sake over two genuinely different I/O models, violating the no-speculative-abstraction rule and adding indirection with no caller benefit. (2) Full separation (duplicate rubric/SignalLevel/metrics into a panel-only package) — rejected: re-duplicates the ~3 modules that are correctly shared today and that BOTH products provably call, creating two rubric definitions that WILL drift. (3) Contract-spine convergence (chosen) — matches what the code already does accidentally; just promotes it to intentional and renames it so the strategic product isn't filed under the legacy one.

- **[P2] Convention-only cross-boundary couplings the type system cannot see (magic strings + duplicated config + untyped Json)**
  - Several load-bearing contracts cross module boundaries with no compile-time guard, only comments. (1) The handoff sentinel 'handing you to my colleague' is a magic string the persona prompt must emit verbatim and `detectsSentinel` must match (panel-machine.ts:95,108) — a leak between the prompt layer (coach-core seat config) and the FSM. (2) The realtime input-session config (turn_detection:null, gpt-4o-transcribe, language:en) is duplicated byte-for-byte in `openai.ts:261-264` (mint) and `realtime-connection.ts` INPUT_SESSION_PATCH, kept in sync only by a 'MUST stay identical' comment — a leak between the server mint boundary and the client transport. (3) `reportJson` shape is hand-mirrored in three places (panel-orchestrator output, mock-schemas.ts mockReportSchema, report UI) with NOTHING validating the assembled output against the schema (verified earlier: orchestrator parses inputs but never runs mockReportSchema on its output). (4) The rubric `name` strings cross from coach-core into `prisma/seed.ts` ownedLPs by hand-copy (comment-enforced at seed.ts:9). All four are real cross-boundary couplings invisible to TypeScript.
  - ref: `src/features/mock-panel/lib/panel-machine.ts:95; src/lib/coach/openai.ts:261-264 + src/features/mock-panel/lib/realtime-connection.ts (INPUT_SESSION_PATCH); packages/shared-types/src/mock-schemas.ts:154 (mockReportSchema unused on output)`
  - why it matters: These are the failure modes that ship green and break in production: a persona prompt reword silently disables natural handoff (falls back to the 14-turn counter), a one-sided config edit degrades transcription on the live call, a reportJson field rename diverges the writer from the reader with no test catching it, a rubric rename orphans a seat. They are concentrated exactly at the inter-module seams this dimension audits, and none is caught by the type system or current tests.
  - fix: Make the highest-blast-radius ones type- or test-enforced. (1) Export the sentinel as a single const from coach-core and have the seat-persona builder INTERPOLATE it into the prompt (so prompt and matcher share one source) rather than the prompt hardcoding it. (2) Define the realtime input-session config ONCE (in shared-types or a shared const) and import it into both the mint body and the client patch — kill the duplication. (3) Run `mockReportSchema.parse()` on the assembled reportJson at the end of `panel-orchestrator` before persist — turn the 'do not let it drift' comment into a runtime assertion. (4) Promote rubric names to a string-literal union in coach-core and type `ownedLPs` against it (or add a consistency test asserting the three string sets agree).
  - alternatives: (1) Leave as comments — rejected: comment-enforced cross-file invariants are exactly the couplings that rot silently, and three of these four cross the most important boundary (prompt<->FSM, mint<->transport, writer<->reader). (2) Heavy codegen / a shared config DSL — rejected as over-engineering for four discrete strings/objects; a const-export + one runtime `.parse()` + one literal union is the surgical fix that matches the existing style. (3) The chosen targeted fixes each remove one specific silent-drift vector without new abstraction layers.

- **[P2] Untyped Json blobs are the real boundary where all schema guarantees stop — and validation is asymmetric across products**
  - Eight Json columns carry both products' actual payloads with no DB-level shape (metricsJson, rubricScoresJson, reportJson, factsJson, disfluencyJson, capabilities, events, seatRollup). They are written with `as unknown as` casts and validated only at SOME reads. The asymmetry is the problem: panel-orchestrator validates metrics/disfluency on read (speechMetricsSchema/disfluencyReportSchema.safeParse), but the coach's `turn-orchestrator.ts` writes `metricsJson: metrics` with no schema on write, and `resume-digest.ts:17` hard-casts factsJson with NO validation before that text flows into interviewer instructions. So the SAME conceptual payload (delivery metrics) is contract-checked in one product and unchecked in the other — a boundary inconsistency, not just a velocity tradeoff.
  - ref: `src/lib/coach/turn-orchestrator.ts:149 (metricsJson write, no schema); src/lib/mock/resume-digest.ts:17 (factsJson hard-cast, no validation, flows to prompt)`
  - why it matters: This is where 'schema-shape guarantees stop' for BOTH products, and the inconsistency means a malformed blob is caught in the panel read path but propagates silently in the coach path / resume path. For the resume case specifically, an unvalidated factsJson becomes part of a live interviewer's grounding prompt — a correctness AND prompt-integrity hole at a product boundary. It is the single largest correctness blind spot in the data model and it sits exactly at the cross-module seam.
  - fix: Validate Json at the WRITE boundary, symmetrically, for the blobs that cross a trust or product boundary: (1) parse `metricsJson` with the shared SpeechMetrics schema before BOTH `practiceTurn.create` (coach) and the panel write — make the metrics contract enforced on write in both products. (2) Add a `ResumeFacts` Zod schema in shared-types and parse it in `resume-digest.ts:17` before the digest is built (today `validateResumeFacts` guards write-time only; a manual DB edit or schema change bypasses it). (3) Keep velocity-only blobs (events, seatRollup) as-is. The principle: any Json that crosses INTO a prompt or ACROSS products gets a write-time schema; internal display blobs stay loose.
  - alternatives: (1) Type every Json column with a Zod schema on both read and write everywhere — rejected as over-correction; the display-only blobs (events, seatRollup, capabilities) gain little and add ceremony. (2) Move blobs to typed relational columns — rejected: the payloads are genuinely variant/evolving (rubric output, report) and relationalizing them would fight the velocity the JSON gives. (3) The chosen rule (write-time schema only where a blob crosses into a prompt or across products) targets the actual trust boundaries and fixes the coach/panel asymmetry without blanket ceremony.

### Test gaps

- (integration / contract) A test that asserts `mockReportSchema.parse()` succeeds on the actual `reportJson` assembled by `panel-orchestrator.ts` (drive runJudgment with synthetic turns, capture the persisted reportJson, parse it against the schema). — _why:_ The schema's own comment says 'Matches panel-orchestrator reportJson EXACTLY — do not let it drift,' but NOTHING validates the output against it today (the orchestrator only validates inputs). This is the single highest-value contract test: it converts a comment-enforced cross-module invariant (writer vs schema vs UI reader) into an enforced one, and it guards the moat deliverable (the report) whose shape three layers depend on.
- (unit / boundary) A consistency test asserting the rubric `name` strings in `REACT_JS_COMPETENCIES` (coach-core), the `lp` fields in `question-bank.ts`, the `topic` fields in `seat-openers.ts`, and the `ownedLPs` arrays in `prisma/seed.ts` are mutually consistent (every seat-owned LP exists as a rubric name; every question lp exists; etc.). — _why:_ This is the most fragile cross-file, cross-package coupling (coach-core package strings hand-copied into the app-side seed) and it is the least tested — a single rename or typo silently mis-targets the report's weakestArea or orphans a seat's coverage, and the only current guard is a comment. The test makes a stringly-typed cross-boundary contract fail loudly at CI.
- (unit) A test asserting the realtime input-session config used at mint (`openai.ts` mint body: turn_detection:null, model gpt-4o-transcribe, language en) is byte-identical to the client INPUT_SESSION_PATCH in `realtime-connection.ts` — ideally by importing one shared const into both and asserting equality, or by snapshotting both. — _why:_ This config is duplicated in two files across the server-mint / client-transport boundary, kept in sync only by a 'MUST stay identical' comment. A one-sided edit silently degrades transcription on every live call with no compile-time or test guard. This test pins the most consequential duplicated-config leak in the panel.
- (unit / contract) A test that the SAME `SpeechMetrics` schema validates both `PracticeTurn.metricsJson` (coach write) and `MockTurn.metricsJson` (panel write) — i.e. feed a coach-produced metrics object and a panel-produced one through one schema and assert both pass. — _why:_ The two products independently produce 'delivery metrics' into identically-named Json columns with no shared write-time contract; the coach doesn't validate on write at all. This test forces the metrics contract to actually converge (the recommended convergence point) and catches the day one product's metrics shape drifts from the other's.
- (unit) A test asserting `detectsSentinel(seatPersona)` returns true for the literal HANDOFF_SENTINEL when given the actual seeded seat persona prompts (or, post-fix, that the persona builder interpolates the exported sentinel const). — _why:_ Natural handoff depends on the persona emitting 'handing you to my colleague' verbatim and the FSM matching it — a prompt<->FSM boundary with zero test coverage. A prompt reword silently degrades handoff to the slow seatBudget fallback. This test guards the prompt/FSM seam that this dimension flags as the highest-blast-radius magic-string leak.

## realtime-state — grade B

The realtime engine is genuinely well-architected for a solo build: a pure, unit-tested FSM (panel-machine.ts, 13 phases) cleanly separated from an effect hook (use-mock-panel.ts) and a headless WebRTC transport (realtime-connection.ts). Turn-taking is correctly belt-and-suspenders push-to-talk (turn_detection:null at BOTH mint openai.ts:263 and client patch realtime-connection.ts:62; create_response off; single-in-flight response gate; interviewer reply triggered by the Done tap not by transcription, use-mock-panel.ts:305-312). The recovery surface is real, not happy-path-only: distinct phases + actions for handoff, TTL re-mint, ICE reconnect (4s flap grace, MAX_RECONNECTS=3, per-attempt re-entry token at use-mock-panel.ts:572), session-expired, judgment-timeout. awaitPlayoutEnd (realtime-connection.ts:262) is a thoughtful anti-clip fix from a real live test. Where a 1-hour live session breaks today: (1) a hard browser refresh mid-panel cannot rehydrate — GET /status returns only {status, scenarioId, maxSeq} (route.ts:74-78) so a reconnect lands on seat 0 with an empty turnsLogRef and no continuity; (2) the turn-queue's drop-after-exhaustion and seq-reconcile hooks are constructed but never wired (use-mock-panel.ts:406-413), so a lost COACH turn silently corrupts the verdict with zero telemetry; (3) the BYOK spend ceiling is inconsistent between /turns (unconditional, turns/route.ts:106) and /mint (keySource-aware, mint/route.ts:109-112), so a paying user's session can be force-wrapped early; (4) a DEBRIEF that never finishes (sweeper down, stuck RUNNING lease) makes the client poll 202 forever — MAX_POLL_ERRORS only counts fetch errors, not 202s. None of the server routes in the realtime path (mint, create, complete, report, turns, status/patch) or the transport have a single test. The FSM is well-tested; everything that performs I/O around it is not.

### Findings

- **[P1] Mid-panel browser refresh cannot rehydrate: reconnect lands on seat 0 with empty history**
  - On a hard refresh during a live multi-seat panel, the hook's in-memory refs (turnsLogRef, seatsRef, ephemeralRef, queueRef, activeSeatIndex) all reset to initialPanelState() defaults. The only rehydrate path is CREATE_DUPLICATE → getStatus → ADOPTED (use-mock-panel.ts:424-429), and reconcileStatus maps LIVE/INTERRUPTED → 'reconnecting' (panel-machine.ts:148-150). doReconnect then mints with seatIndex: s.activeSeatIndex (use-mock-panel.ts:508), which is 0 from the fresh state, and replays an EMPTY turnsLogRef (replayOnConnectRef set but the log is []). GET /status (route.ts:74-78) returns ONLY {status, scenarioId, maxSeq} — NOT activeSeatIndex and NOT seats — so the client physically cannot rebuild a mid-panel session. seatsRef is also empty on this path, so activeSeatId() returns null and every subsequent turn is written with seatId:null, which mis-attributes scoring. A candidate 40 minutes into a 1-hour interview who refreshes is silently thrown back to interviewer #1 with no memory.
  - why it matters: This is the single most likely way a real 1-hour session breaks: a refresh, a tab crash, or an OS-level WebRTC reset mid-interview. The product's whole value is the multi-seat panel arc; reconnecting to seat 0 with no history destroys that arc and corrupts the per-seat transcript the judge scores. It is invisible to every existing test because the FSM tests feed clean synthetic CREATE_OK actions that populate seats.
  - fix: Extend GET /status to return activeSeatIndex (derive from completed handoffs or store it on MockSession), the seats array, and keySource, then have an ADOPTED→LIVE/INTERRUPTED path that (a) re-fetches seats into seatsRef, (b) rebuilds turnsLogRef from the server's MockTurn rows (you already store transcript+role+seq), and (c) calls queue.reconcileSeq(maxSeq) before the first enqueue. The seat index can be reconstructed from the count of distinct completed seatIds in MockTurn, or stored explicitly as MockSession.activeSeatIndex updated on each handoff mint.
  - alternatives: Persisting full client state to localStorage was considered but is worse here: the ephemeral is short-TTL and dead after a refresh anyway, the queue's in-flight body must re-derive seq from the server (the authority), and seats/transcript already live in Postgres — localStorage would just be a stale, drift-prone mirror of the DB. Blocking refresh with a beforeunload prompt is user-hostile and doesn't survive a real crash. Server-side state extension is the minimal, source-of-truth-correct fix.

- **[P1] Turn-queue drop/reconcile hooks are unwired: a lost COACH turn silently corrupts the verdict**
  - createTurnQueue is constructed with only { post, fetchMaxSeq, onSessionExpired } (use-mock-panel.ts:406-413). The queue defines onCommitted and onDeliveryError hooks and a reconcileSeq method (turn-queue.ts:34-46), and its own fail() comment states 'a lost COACH turn would corrupt the verdict' (turn-queue.ts:60-62). But the hook passes neither onDeliveryError nor onCommitted, and never calls reconcileSeq at session adoption. So when an item is dropped after 8 attempts (network partition during a long answer, repeated not-live), fail() shifts it off the queue and NOTHING surfaces it — no toast, no log, no telemetry, no degraded-mode flag on the report. The candidate receives a verdict computed on an incomplete transcript and cannot tell. Separately, because reconcileSeq is never invoked on rehydrate, the seq cursor is never re-synced to the server's maxSeq after an adopt — the first enqueue starts at seq 0 and immediately SEQ_CONFLICTs against existing rows, burning retries.
  - why it matters: COACH turns are the Bar-Raiser drill-depth scoring input; dropping one quietly changes the verdict, which is the product's deliverable AND the A1 outcome-calibration label the whole moat depends on. Silent corruption of the scoring corpus is worse than a visible error. Over a 1-hour session on a flaky network, an 8-attempt exhaustion is plausible.
  - fix: Wire onDeliveryError to set a degraded-delivery flag that (a) is sent on complete() so the report can mark itself 'partial transcript', and (b) surfaces a non-fatal banner. Wire onCommitted for spend/telemetry if useful. Call queueRef.current.reconcileSeq(maxSeq) right after a successful getStatus on the duplicate/adopt path before any enqueue. At minimum, log.warn on drop so it's observable.
  - alternatives: Making COACH turn delivery infinitely-retried (never drop) was considered but rejected: an unbounded retry would hang drainBeforeComplete and prevent the user from ever reaching their report — the current bounded-drop is the right safety choice, it just needs to NOT be silent. Reconstructing the dropped turn server-side from the OpenAI transcript isn't possible because Aloud is never in the audio path.

- **[P1] BYOK spend ceiling is enforced inconsistently between /turns and /mint**
  - mint/route.ts:109-112 correctly applies only MAX_SESSION_SEC to BYOK (keySource === 'USER') sessions and the dollar ceiling only to house sessions: `over = keySource === 'USER' ? elapsedSec >= MAX_SESSION_SEC : isOverCeiling(...)`. But turns/route.ts:106 calls `isOverCeiling(spendCents, elapsedSec)` UNCONDITIONALLY, independent of keySource, and returns sessionExpired:true once the synthetic spendCents crosses SESSION_CEILING_USD. The turn-queue forwards sessionExpired → onSessionExpired → SESSION_EXPIRED action → 'wrapping' (panel-machine.ts:267-268). So a BYOK user whose server-clock estimate crosses the house dollar ceiling (~$4) gets their session force-wrapped from the /turns path mid-interview, even though their own key is paying and only the time stop should apply. The two checkpoints disagree on the same session.
  - why it matters: The entire BYOK pitch is 'your key, your minutes, no house dollar cap — only a time stop.' A BYOK candidate doing a genuine 1-hour interview will cross the synthetic $4 ceiling well before MAX_SESSION_SEC and be cut off early by the turns checkpoint, contradicting the mint route's own policy and the product promise. It's a correctness divergence, not a safety one (the user is paying), so it strictly harms the paying user.
  - fix: Pass keySource into the turns route's check (the row already has it — add keySource to the select at turns/route.ts:46) and mirror the mint route's branch: `sessionExpired = keySource === 'USER' ? elapsedSec >= MAX_SESSION_SEC : isOverCeiling(spendCents, elapsedSec)`. Better: extract a single `isSessionOver(keySource, spendCents, elapsedSec)` helper in spend.ts and call it from BOTH mint and turns so the policy lives in one place.
  - alternatives: Leaving /turns as a belt-and-suspenders house guard was considered, but it can't be 'belt and suspenders' when it enforces a DIFFERENT policy than the authoritative mint gate — it actively contradicts it for the BYOK case. Removing the ceiling check from /turns entirely is worse: house sessions genuinely need a per-turn stop because a user could otherwise avoid re-minting. Centralizing the predicate is the only consistent fix.

- **[P2] DEBRIEF that never completes makes the client poll 202 forever (sweeper/lease failure mode)**
  - The report route returns FAILED only when ageSec > 180 AND the job is exhausted (status FAILED or attempts >= 3) (report/route.ts:55-58). If the judgment job is stuck — sweeper process down, or a job claimed RUNNING whose lease hasn't expired because the worker hung without crashing — it stays PENDING/RUNNING-with-live-lease and attempts stays < 3, so `exhausted` is false and the route returns 202 indefinitely. On the client, doPoll only increments pollErrorsRef on r.kind === 'error' (a fetch failure), NOT on r.kind === 'debrief' (use-mock-panel.ts:550-552), so a steady stream of 202s reschedules forever with no bound. The user sees an eternal 'panel is conferring' spinner with no path to a report or an error.
  - why it matters: After a full 1-hour interview, the report IS the payoff. A stuck judge (the sweeper relies on a single in-process setInterval per server, instrumentation.ts; on the single-EC2 deploy a process restart between complete() and the next sweep, or a hung gpt-4o-mini call holding a lease, is plausible) leaves the candidate staring at a spinner forever. The 180s deadline only fires when attempts are exhausted, which a non-crashing hang never reaches.
  - fix: Make the report-route deadline a hard wall: if ageSec > JUDGMENT_DEADLINE_SEC, return FAILED('judgment_timeout') regardless of job.attempts (the lease sweeper will still retry server-side, but the client must not spin forever). Independently, add a client-side absolute poll budget (e.g. stop after N total polls or T elapsed) that dispatches REPORT_FAILED('judgment_timeout'), so the client is self-protecting even if the server contract changes.
  - alternatives: Shortening the lease so stuck RUNNING jobs re-claim faster helps the retry path but doesn't bound the CLIENT — the client must have its own deadline. Counting 202s toward MAX_POLL_ERRORS was considered but conflates 'healthy still-working' with 'error'; an explicit elapsed/absolute-count budget is clearer and matches the server's own 180s intent.

- **[P2] Natural handoff depends on an exact magic-string the persona must emit verbatim, with no seed guarantee**
  - detectsSentinel does a lowercased substring match on the literal 'handing you to my colleague' (panel-machine.ts:95,108-110), and COACH_DONE only triggers a natural handoff when that substring is present OR exchangeCount hits seatBudget (14/18, panel-machine.ts:222-229). The seat persona prompt must emit that exact phrase. There is no test asserting the seeded seat systemPrompts actually contain it, and the model can easily paraphrase its closing line ('let me pass you to my colleague', 'I'll hand over now'). When it does, the sentinel never fires and the seat only ends when the generous safety counter (14 exchanges, ~15 min) trips — turning a natural ~5-exchange segment into a marathon and blowing the 1-hour budget across 3 seats.
  - why it matters: A persona-prompt edit (or just model nondeterminism) silently degrades handoff timing, which directly controls total interview length and whether all 3 seats fit in an hour. It's a load-bearing coupling held together by a string literal in two files plus a comment.
  - fix: Two layers: (1) add a seed/contract test that asserts every non-Bar-Raiser seat's systemPrompt contains HANDOFF_SENTINEL (or, better, instruct the persona to emit a structured marker the data channel can't paraphrase — e.g. a sentinel token the prompt is told to output literally at handoff). (2) Loosen detection to a small set of paraphrase patterns as a fallback before relying on the counter. Keep the counter as the last-resort safety valve only.
  - alternatives: Driving handoff purely off the exchange counter (drop the sentinel) was rejected by the team deliberately — the comment at panel-machine.ts:97-103 explains the counter alone reproduced the 'forced to finish fast' live-test failure, so the persona-decides-depth model is correct. A function-call/tool-based handoff signal would be more robust but adds realtime tool-calling complexity the rest of the engine avoids; a literal sentinel token the prompt must echo is the cheapest robust upgrade.

- **[P2] Same-seat TTL re-mint and reconnect tear down the peer WITHOUT awaitPlayoutEnd, risking mid-sentence clips**
  - doHandoff and doWrap both call `await peerRef.current?.awaitPlayoutEnd()` before closePeer() (use-mock-panel.ts:455, 529) — the documented anti-clip fix. But doRemint (use-mock-panel.ts:478) and doReconnect (use-mock-panel.ts:501) call closePeer() immediately with no awaitPlayoutEnd. doRemint fires from the TTL watchdog, which is gated to fire only when idle (!speaking && !coachResponseInFlight, use-mock-panel.ts:610-611), so a clip there is unlikely. doReconnect, however, fires on a real ICE drop that can land mid-interviewer-sentence; closePeer() pauses remoteAudio instantly (realtime-connection.ts:308), so the candidate loses the tail of the interviewer's line, then on resume the persona replays history and continues — a jarring discontinuity. Less severe than handoff (it's an error path) but the same clip class the team already fixed once.
  - why it matters: Over a 1-hour session, transient ICE 'disconnected' events are routine on real networks; the 4s grace catches flaps, but a genuine reconnect after the grace will clip whatever the interviewer was saying. It's a polish/continuity regression in exactly the dimension (handoff/continuity) the team has invested in.
  - fix: This is a judgment call, not a clear bug: on a real disconnect the audio may already be dead, so awaiting playout could just burn the 9s timeout. Recommend NOT adding awaitPlayoutEnd to doReconnect (the stream is gone) but DO ensure the post-reconnect replay re-establishes context cleanly (it does, via replayOnConnectRef). For doRemint, the idle-gate already prevents the clip; leave it. Document the asymmetry so it's an intentional decision, not an oversight.
  - alternatives: Adding awaitPlayoutEnd everywhere was considered and rejected: on an ICE failure the remote track is already silent, so awaitPlayoutEnd would either resolve instantly (no analyser signal) or wait the full backstop, delaying recovery. The current placement (only on graceful handoff/wrap where audio is genuinely still playing) is actually correct — the finding is to confirm it's deliberate, not to change it.

- **[P3] Config-lock between mint and client patch is duplicated and comment-enforced only**
  - The realtime input session config (type:'realtime', transcription gpt-4o-transcribe language:en, turn_detection:null) is written in two places: the mint body (openai.ts:261-264) and the client INPUT_SESSION_PATCH (realtime-connection.ts:62-70), kept in sync only by 'MUST stay identical to the mint-time config' comments. The client re-asserts it on dc.onopen as belt-and-suspenders. If one drifts (e.g. someone flips turn_detection to semantic_vad in the patch but not the mint, or changes the transcription model), turn-taking or transcription silently degrades with no compile-time guard. The shapes are slightly different already (the mint nests under session.audio.input; the patch is the audio object directly), so a literal shared constant isn't drop-in.
  - why it matters: A silent transcription/turn-detection drift would either re-introduce the mid-answer cutoff (if VAD comes back on) or produce an empty interview the judge scores as a failure — both are 1-hour-session-breaking, and both would pass tests since neither file is tested.
  - fix: Extract the input-config primitives (model name, language, turn_detection value) into one shared constant in coach-core or shared-types and reference it from both the mint body and the client patch, so a change in one is impossible to make without the other. If the nesting difference blocks a single object, at least share the leaf values (transcription model, language, turn_detection literal).
  - alternatives: A runtime assertion comparing the two configs was considered but they live on different sides of the network (server mint vs client patch) so there's no single place to assert. Sharing leaf constants is the minimal enforcement that the type system can actually check.

## Testing strategy & coverage — grade C+

The repo has a competent, fast (243 tests / 26 files, 3.4s green) bottom-of-the-pyramid: pure coach-core logic and security primitives are genuinely well-tested (panel-composition Bar-Raiser veto, AES-GCM tamper rejection, turn-queue seq idempotency, spend-meter boundary math). That foundation is real and the mocking convention (vi.hoisted + vi.mock of @/lib/*) is consistent and copy-able. But the test pyramid is INVERTED at the value axis: the most expensive-to-get-wrong code is the least tested. The mint route (189 LOC — credential minting + per-session spend ceiling + BYOK-vs-house ceiling divergence + CSRF + ownership + state transitions) has ZERO tests (confirmed: no test imports mint/route). The session-create, complete, and report routes — the two ends of the core product flow — are untested. panel-orchestrator.ts (293 LOC, the moat scoring GLUE that assembles reportJson and writes the Outcome label) and judgment-queue.ts (94 LOC, lease-based claim) have no tests; their pure helpers are tested but the orchestration wiring is not. realtime-connection.ts (324 LOC, parses untrusted Realtime events) is untested with no extracted pure mapping fn. ## security-observability — grade B-

Security custody is genuinely strong and disciplined; observability is near-absent and is the real liability for a product that spends real money per minute. Confirmed by reading the files: the BYOK secret path is tight — the raw `sk-` key touches exactly three frames (validate via discarded mint, encrypt on POST, decrypt only inside the mint call frame), is never echoed/re-stored/placed in an Error, and `ProviderError` (openai.ts:11-19) carries only `code + status`, never `await res.text()` (which can echo the Authorization header). Redaction is centralized at the log SINK (log.ts:18 → redactUnknown), so even routes that pass raw `err` are scrubbed of sk-/sk-ant-/ek_/AIza/Bearer (redaction.ts:13-19). AES-256-GCM with fresh 12-byte IV, stored tag, fail-closed `kek()` (crypto.ts:35-43). Auth is defense-in-depth (proxy gate + per-route `await auth()` + userId-scoped Prisma). The atomic daily kill-switch (spend.ts:46-50) and server-clock spend meter are correct.\n\nBut three structural weaknesses pull the grade down. (1) SECRET CUSTODY BLAST RADIUS: a single global KEK = sha256(KEY_ENCRYPTION_SECRET) encrypts EVERY user's billing-enabled key; it lives in plain process env, there is no per-record DEK / KMS envelope (dekVersion=1 is a marker only), and no detection on bulk decrypt. (2) OBSERVABILITY IS A NEAR-VACUUM: grep confirms ZERO OpenTelemetry/Sentry/StatsD/Prometheus anywhere in src/packages; the only sink is log.ts → stdout; the health route (health/route.ts) is a trivial liveness probe with no DB/OpenAI/cap check; there are NO correlation/request IDs, NO success-path or spend telemetry, and logging is 1-2 calls per route concentrated in catch blocks. Most damning: the global daily kill-switch trips SILENTLY — reserveGlobalSpend returning false → 503 emits no log line (sessions/route.ts:128-133), so the single most important money-defense event in the product is invisible to operators. (3) `redactUnknown` (redaction.ts:31-33) reduces every Error to `name: message`, DROPPING the stack — safe for leaks but it means 500s are nearly undebuggable. Net: you can hold a user's paying key safely but you cannot see, debug, or alert on what that key is spending.

### Findings

- **[P1] Daily spend kill-switch trips silently — the #1 money-defense event emits no log/metric/alert**
  - reserveGlobalSpend (spend.ts:39-51) is the global daily kill-switch: an atomic add-if-under-cap UPDATE that returns false when DAILY_CAP_USD ($50 default) would be exceeded. At the one call site (sessions/route.ts:128-133), a false return produces `503 'At capacity, try again shortly'` and NOTHING ELSE — no log.warn, no metric, no alert. Grep for alert|pagerduty|slack|webhook|notify across src/+packages returned zero hits. So the moment the product hits its house-cost ceiling and starts refusing all trial users, operators learn nothing until a human notices users complaining. There is also no telemetry on cap PROXIMITY (e.g. 80% consumed), so there is no early warning either.
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/src/lib/mock/spend.ts:39-51 and /Users/princesahoo/CODE/Academic Projects/sevenlabs/src/app/api/mock/sessions/route.ts:128-133`
  - why it matters: This is a product that 'spends real money per minute.' The daily cap is the last line of defense against a cost blowout (runaway sessions, an abusive user, a pricing miscalculation). A kill-switch that fires invisibly is half a kill-switch: it prevents the financial bleed but gives operators zero signal that something is wrong, turning a contained incident into a silent outage. For a solo-founder product with no on-call, silent failure is the worst failure mode.
  - fix: At minimum, log.warn('[spend] daily cap reached', { day, holdUsd, capUsd }) when reserveGlobalSpend returns false, and log.info the running GlobalSpend.estUsd on every successful house reservation so a log-based alert can fire at 80%.   - alternatives: Full OTel metric (spend_reserved_usd gauge + alert rule) is the 'correct' answer but is over-engineered for current scale with no metrics backend wired — it would be the first OTel dependency in the repo. A Stripe-style hard external budget API doesn't exist here. The DB-poll-and-webhook approach is worse for latency (up to 5 min lag) but far better for THIS codebase: zero new runtime deps, reuses GlobalSpend, and the cap is a daily not per-second bound so 5-min granularity is fine.

- **[P1] No request correlation ID and no spend/key-source telemetry — a per-minute-billing flow is unobservable end-to-end**
  - Verified: there is no x-request-id / correlation-id / trace-id propagation anywhere (grep returned only clientRequestId, which is an idempotency key on the create body, NOT a log-propagated correlation id). So given a billing dispute or an OpenAI invoice spike, there is no way to reconstruct from logs which sessions ran on the house key, how long they ran, or who they belonged to. The mint-failure logs (mint/route.ts:179-182, sessions/route.ts:191-194) deliberately log only { sessionId, status } — good for leaks, but a single session's lifecycle (create→mint→remint×N→complete→judge) cannot be stitched together because each log line is independent with no shared id.
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/src/app/api/mock/sessions/[id]/mint/route.ts:163-184 and /Users/princesahoo/CODE/Academic Projects/sevenlabs/src/app/api/mock/sessions/route.ts:135-196`
  - why it matters: Observability for a money-spending product is not optional polish — it is the audit trail for the dollars. Without a correlation id you cannot answer 'why did this session cost $X' or 'show me all events for session abc123'; without success-path spend logs you cannot detect cost anomalies before the monthly invoice.   - alternatives: A full tracing layer (OTel spans across create→mint→judge) would give the richest view but requires a collector + backend that don't exist and would be the repo's first APM dependency — disproportionate now. AsyncLocalStorage-based request-id injection is the idiomatic Next.js approach and is the right medium-term move, but for THIS codebase sessionId is already a perfect business-level correlation key that survives across requests (unlike a per-request id), so threading it is both cheaper and more useful than a generic request id today.

- **[P1] Single global KEK in plain process env, no per-record DEK / KMS envelope, no decrypt-anomaly detection**
  - crypto.ts:35-43: the content-encryption key is sha256(KEY_ENCRYPTION_SECRET) — ONE static 32-byte key for ALL users' billing-enabled provider keys. It is loaded into Node process.env (env.ts:24) and used directly in app code, so it has the same blast radius as any other env var (a process dump, an accidentally-logged process.env, an AWS task-def exposure decrypts every stored key). dekVersion=1 (schema.prisma) anticipates a KMS envelope but it is NOT built; env.ts:23 admits rotation 'invalidates all stored ProviderKeys.' There is no per-record DEK, no envelope, and crucially no detection/alert on bulk ProviderKey decryption (resolveSessionKey decrypts in-frame with no counter or log).
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/src/lib/crypto.ts:35-43 and /Users/princesahoo/CODE/Academic Projects/sevenlabs/src/lib/byok.ts:29-42`
  - why it matters: The entire product pitch is 'we hold your paying OpenAI key, encrypted.' The encryption is correct (authenticated AES-256-GCM), but the KEY-MANAGEMENT around it is the weakest link: compromise of the web container = compromise of every user's key at rest, with no rotation path short of invalidating everyone, and no way to even notice exfiltration because decrypts are silent.   - fix: Before onboarding real paying users: (1) move KEY_ENCRYPTION_SECRET out of plain task-def env into AWS Secrets Manager fetched at boot (reduces task-def exposure), and (2) implement the dekVersion>=2 KMS envelope the schema already anticipates — a per-record DEK wrapped by a KMS CMK, so a DB dump alone is useless without KMS Decrypt permission and KMS gives you CloudTrail decrypt logging for free (solving the no-detection gap). (3) Interim, emit a log.info on every resolveSessionKey decrypt so a baseline decrypt rate exists to alert on.
  - alternatives: Per-user KEK derived via HKDF(masterSecret, userId) limits blast radius cheaply (no new infra) but still keeps the master in process env and still has no audit trail — strictly better than today but inferior to KMS. Rotating to a new env KEK periodically helps nothing while the scheme is all-or-nothing. KMS is the right target because it simultaneously fixes blast radius (CMK never leaves KMS), rotation (CMK rotation is automatic), AND detection (CloudTrail) — the three gaps at once — and the schema's dekVersion field shows it was already the intended design.

- **[P2] redactUnknown drops the Error stack entirely — 500s are nearly undebuggable**
  - redaction.ts:31-33: for an Error, redactUnknown returns only redact(`${value.name}: ${value.message}`) — the stack is discarded. Every top-level catch in the API routes funnels raw `err` through log.error → log.ts:18 → redactUnknown (sessions/route.ts:198, mint/route.ts:186, register/route.ts:47, keys/route.ts:142). So an unexpected 500 logs e.g. 'Error: undefined is not a function' with NO file/line/frame. This is a real observability gap (the leak-safety is good; the debuggability is poor).
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/packages/coach-core/src/redaction.ts:30-40`
  - why it matters: When a production 500 fires, the on-call (the founder) gets a message with no stack — they cannot tell which of the ~5 awaited operations in a route threw. Combined with the absence of correlation ids and the trivial health check, a production incident in the mock flow is close to a black box. Stack traces do not contain secrets in the patterns this codebase produces (secrets are in headers/bodies, not call frames), so redacting them away costs debuggability for little leak-safety gain.
  - fix: Include the redacted stack for Error values: in redactUnknown, when value instanceof Error, return redact(`${value.name}: ${value.message}\n${value.stack ?? ''}`) — redact() still scrubs any sk-/ek_/Bearer that might appear in a frame's message. This keeps the leak guarantee (the stack still passes through redact) while restoring the single most useful debugging artifact.
  - alternatives: Keeping stacks out for paranoia is defensible only if stacks routinely carried secrets — they don't here (the codebase never interpolates a key into a thrown message; ProviderError is code+status). A structured error object with separate fields (name/message/stack) would be cleaner than a concatenated string but is a larger change; concatenating through the existing redact() is the minimal, leak-safe fix for THIS sink design.

- **[P2] Health endpoint is a bare liveness probe — green health says nothing about DB, OpenAI, or spend-cap state**
  - health/route.ts:7-16 returns a static {status:'healthy', timestamp, version} with no checks. It never touches Prisma (so a dead DB still reports healthy), never validates env/KEK config, never surfaces whether the daily cap is exhausted. The ALB will keep routing traffic to a task whose DB connection is gone or whose KEK is misconfigured (BYOK silently 503ing), because the health probe is decoupled from every dependency that actually matters.
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/src/app/api/health/route.ts:7-16`
  - why it matters: For an ECS/ALB deployment, the health endpoint is the system's primary external signal. A liveness-only check means the most common real failures (DB unreachable, KEK unset so BYOK is off, daily cap hit) are invisible to the load balancer and to any uptime monitor pointed at /api/health — the product can be functionally down while every dashboard is green.
  - fix: Add a shallow readiness check: SELECT 1 against Prisma (with a short timeout), assert isByokConfigured() if BYOK is expected, and optionally include the day's GlobalSpend.estUsd vs cap. Return 503 if the DB check fails so the ALB drains the task. Keep a separate liveness path if you want ALB liveness vs readiness split.
  - alternatives: A deep health check that pings OpenAI on every probe would burn quota and add latency/flakiness to the ALB loop — worse. The right scope for THIS app is DB-reachability + config-sanity (cheap, deterministic) and leaving provider reachability to the spend/mint error paths, which already degrade gracefully (502 'Voice unavailable').

- **[P2] Rate limiter is a non-atomic read-after-write window — burstable under concurrency, and rows never reaped**
  - checkRateLimit (spend.ts:86-99) upserts a RateBucket row then reads bucket.count <= limit. Two concurrent requests in the same window can each increment and each observe count <= limit before the other commits (no SELECT FOR UPDATE / atomic conditional like reserveGlobalSpend uses), so the limit is soft and burstable. Fixed windows also permit ~2x burst at the boundary. RateBucket rows are never garbage-collected (unbounded table growth). This guards the credential-minting endpoints (keys POST 5/hr, mint 10/min) — the exact surfaces an attacker would hammer (validateKeyViaMint is also a key-validity oracle against OpenAI).
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/src/lib/mock/spend.ts:86-99 and /Users/princesahoo/CODE/Academic Projects/sevenlabs/src/app/api/keys/route.ts:176-188`
  - why it matters: The rate limiter sits in front of money-spending and key-validating operations. A soft, burstable limit means the 'limit' is an upper-ish bound, not a guarantee — an attacker with concurrent requests can exceed it, and the validateKeyViaMint oracle plus unlimited DELETE (DELETE /api/keys has no rate limit at all — keys/route.ts:176-188 goes through guard() only) widen the abuse surface. Unbounded RateBucket growth is also a slow DB bloat.
  - fix: Make the limit atomic like reserveGlobalSpend already is: a single conditional UPDATE that increments only when count < limit and checks affected rows, in one statement. Add a per-IP limit to POST /api/keys (currently per-user only) and a rate limit to DELETE. Reap RateBucket rows older than the window with a periodic DELETE (or a TTL job).
  - alternatives: A Redis token-bucket (atomic INCR+EXPIRE) is the standard answer and gives free TTL reaping, but adds a Redis dependency this single-Postgres deploy doesn't have. Given reserveGlobalSpend already proves the atomic-conditional-UPDATE pattern works in this exact codebase, reusing it for rate limits is strictly better here than introducing Redis: no new infra, same proven idiom, and it closes the concurrency hole.

- **[P2] No script-src CSP on a page that handles a pasted API key — self-acknowledged 'P1 gate before BYOK' shipped anyway**
  - next.config.ts:8-14 sets X-Frame-Options, frame-ancestors 'none', Permissions-Policy microphone=(self), nosniff — but NO Content-Security-Policy script-src. The comment (lines 3-4) explicitly calls script-src CSP 'the P1 gate before BYOK' and defers it. The BYOK key-paste form (key-management.tsx) takes a plaintext sk- key into an input; without script-src, any XSS anywhere in the app could read the key from the form's DOM before submission.
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/next.config.ts:3-14`
  - why it matters: The single highest-value secret in the product (a user's live billing key) is entered into a form that is not protected by the one header that defends against script injection. The repo's own comment classifies this as the P1 prerequisite for BYOK, and BYOK is built — so the gate was bypassed. An XSS that would otherwise be a session-hijack becomes a key-exfiltration.
  - fix: Land a script-src CSP with per-request nonce wiring (Next supports nonce via middleware/headers) before BYOK reaches real users, matching the codebase's own stated gate. Start in report-only mode to find inline-script violations, then enforce.
  - alternatives: A hash-based CSP avoids nonce plumbing but is brittle with Next's injected inline bootstrap scripts; 'unsafe-inline' defeats the purpose. The nonce approach is more work but is the only one that actually protects the key-paste surface for a Next App Router app — and the config comment already scoped it as the intended solution.

- **[P2] Origin/CSRF guard is bypassed when the Origin header is absent (origin && host && ...)**
  - badOrigin (keys/route.ts:28-32) and the inline mint check (mint/route.ts:52-55, sessions/route.ts:43-47) only reject when BOTH origin AND host are present: `origin && host && new URL(origin).host !== host`. A request with no Origin header passes the check entirely. Since auth is a JWT-in-cookie, a state-changing POST/DELETE with a stripped Origin relies solely on Auth.js's own CSRF + SameSite cookie — this hand-rolled guard gives false assurance for the no-Origin case.
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/src/app/api/keys/route.ts:28-32 and /Users/princesahoo/CODE/Academic Projects/sevenlabs/src/app/api/mock/sessions/[id]/mint/route.ts:52-55`
  - why it matters: These are exactly the credential-minting / key-mutating endpoints where CSRF matters most. The guard reads as a CSRF defense but has a hole for the no-Origin case; a reader (or future maintainer) trusts it more than they should. It is not a full break (SameSite cookies are the real backstop) but it is a misleading control on the most sensitive routes.
  - fix: Treat a missing Origin on a state-changing request as suspect: require Origin (or Sec-Fetch-Site: same-origin) to be present and matching for POST/DELETE on /api/keys and the mint routes, rejecting when it is absent rather than allowing. Document that SameSite is the primary defense and this is belt-and-suspenders.
  - alternatives: Relying purely on Auth.js CSRF + SameSite=Lax cookies is defensible and may already cover it — but the code chose to add an explicit origin guard, and a guard with a silent bypass is worse than no guard (false confidence). Tightening the existing check to fail-closed on missing Origin is a one-line change that matches the intent already in the code.

- **[P3] Registration leaks email existence via a distinct 409 (+ bcrypt timing), undercutting its own no-leak comment**
  - register/route.ts:25-32 returns 409 with 'Unable to create account with this email' when the email exists, but a NEW email proceeds to bcrypt.hash + create and returns 200 with the user. So the status code (409 vs 200) and the response shape directly reveal whether an email is registered — the comment 'Don't leak whether the email exists' is not achieved. Additionally bcrypt.hash runs only on the new-account path, so existing emails return measurably faster (timing oracle).
  - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/src/app/api/auth/register/route.ts:25-43`
  - why it matters: Email enumeration lets an attacker build a list of valid accounts to target with credential-stuffing or the account-linking pre-registration attack (register victim@x.com via Credentials, then victim's Google login auto-links via allowDangerousEmailAccountLinking). Low severity alone, but it compounds with the dangerous-linking setting.
  - fix: Return the same status/body for both existing and new emails (e.g. always 200 'check your email' if you add verification, or a generic 400/409 for both), and normalize timing (run a dummy bcrypt on the existing-email path) so the response is constant-time and content-stable.
  - alternatives: True anti-enumeration requires email verification (send-link-on-signup) so the 200 reveals nothing actionable — the right long-term fix and a prerequisite given the account-linking risk. Short of that, equalizing status+timing closes the trivial oracle. Doing nothing is the current state and is the weakest option given the linking setting amplifies it.

- **[P3] No-console lint rule is stated-but-unenforced; one client console.error already bypasses the redaction sink**
  - log.ts:7-8 says a no-console lint rule 'will enforce it once the existing call sites are migrated' — i.e. it is NOT yet enforced. Grep found one live bypass: practice-vad.tsx:70 `init().catch(console.error)`. That specific case is client-side VAD init (not secret-bearing), so no leak today, but the guarantee 'every log goes through redact()' is convention-only.   - ref: `/Users/princesahoo/CODE/Academic Projects/sevenlabs/src/lib/log.ts:7-9 and /Users/princesahoo/CODE/Academic Projects/sevenlabs/src/features/speaking-coach/components/practice-vad.tsx:70`
  - why it matters: The entire secret-leak guarantee rests on 'all logs go through log.ts.' That invariant is currently enforced by reviewer discipline, not by tooling — exactly the kind of guarantee that erodes as the codebase grows. The one existing bypass proves the gap is real.
  - fix: Enable the no-console ESLint rule now (allow it only in log.ts and explicitly-annotated client files), so the redaction invariant is mechanically enforced rather than aspirational. Migrate practice-vad.tsx:70 to a client-safe logger or annotate it.
  - alternatives: Leaving it to review is the status quo and is the weakest option for a security invariant. A runtime console patch (monkey-patching console.* to route through redact) would catch everything including deps but is heavy-handed and surprising; a lint rule is the proportionate, standard enforcement for app code in THIS repo.

## Maintainability — grade C+

Aloud is a two-product Next.js monorepo with a genuinely good *intended* architecture: a pure-logic core (packages/coach-core, verified zero-I/O), a thin BFF, schema-as-contract via Zod, and a clean pure-reducer/effect split in the panel FSM. Where modules are wired, the conventions are coherent and the code reads well. But the maintainability surface is undermined by one catastrophic and several structural issues that will actively hurt a new engineer (or future-self in 6 months).

THE DEFINING PROBLEM (verified empirically, not just asserted): the entire BYOK + resume + Outcome increment is built in the working tree but NOT in git, AND tracked files now `import` untracked modules. `src/app/api/mock/sessions/[id]/mint/route.ts:16-17` and `.../sessions/route.ts:16-17` import `@/lib/mock/resume-digest` and `@/lib/byok`; `packages/coach-core/src/index.ts` re-exports `./resume`, `./panel-context`, `./realtime-cost`. None of this is wrong at runtime, but each is a small lie a new engineer must decode.

What's genuinely good and lowers the grade-floor risk: the pure/I-O boundary is real and tested, idempotency/userId-scoping conventions are consistent, the FSM is exhaustively typed, and a cluster of 9 dead-but-harmless schemas (verified 0 consumers) is the only schema rot. The architecture is maintainable *in principle*; it's the release discipline, doc hygiene, and absence of automated guardrails that drag it to C+. Fixing the P0 commit + landing 3-4 cheap CI guards (typecheck, migrate-diff, lint rules, .tsx glob) would move this to B+ quickly.

## Completeness critic (adversarial review of the synthesis)

**Verdict:** Act on it — but only Phase 0 (and the spend-reconciliation gap) as-is; the two P0s, the four structural gaps, and the gated-yet-pre-decided coach contradiction must be resolved before Phases 1-4 are trustworthy. Every load-bearing empirical claim I checked (dirty tree, migration drift, stubbed confidence, unwired queue hooks, ceiling divergence, unrehydratable status, unversioned verdict) is TRUE; the design's weaknesses are in over-cautious sequencing (D2, D9), a moat-corruption blind spot (D6 still writes the bad label), an unanalyzed real-vs-estimated spend signal, and an undesigned outcome-capture funnel — fixable, not fatal.

### Missing areas the synthesis omitted

- SPEND RECONCILIATION AGAINST REAL USAGE (verified gap, money-correctness): the server-side ceiling AND the GlobalSpend daily kill-switch are driven entirely by spendCentsForElapsed() — a flat clock estimate (spend.ts:24). The client DOES measure real OpenAI token cost via onUsage->turnCostUsd (use-mock-panel.ts:342-343) but it only updates spendUsdRef for a display value and an opt-in client cap; it is NEVER posted to the server, and complete/route.ts never calls settleReservation with it (grep: zero refs). So settleReservation (spend.ts:65) reconciles GlobalSpend against the SAME estimate it reserved against — the daily $50 house kill-switch tracks a fiction that can diverge arbitrarily from the actual OpenAI invoice. The design's D7 unifies only the two clock-gate checks and Phase 3 only fixes the float math (spend.ts:72); neither names the deeper problem that the authoritative spend signal is an estimate while a real one is measured and thrown away. For a product whose pitch is 'we spend real money per minute,' a daily cap that cannot see real spend is a structural hole the design omits.

- JUDGMENT-QUEUE FAILURE SEMANTICS ARE MIS-CHARACTERIZED, so the prescribed test guards the wrong thing: the design (testStrategy + D6) calls for testing 'judgment-queue lease-release-on-throw.' But judgment-queue.ts:60-66 already actively resets status to PENDING on a CAUGHT non-exhausting throw and marks FAILED on exhaustion in a $transaction (lines 49-59) — there is no lease to 'release' on a caught throw. The ONLY genuine stuck-RUNNING path is an UNCAUGHT crash / process death mid-runJudgment, recovered solely by the lease-expiry sweep (claimNext: 'RUNNING AND leaseUntil < now()'). The design never tests the crash/expiry path (the real durability risk) and instead specifies a test for a release-on-throw mechanism that the code doesn't use. This is a missing failure-mode (process death between claim and write) dressed as a covered one.

- DATA LIFECYCLE / DELETION CASCADE for the moat tables and custody: the design extensively covers key custody at rest (KMS, D9) but never addresses what happens to ProviderKey / ResumeProfile / Outcome / MockTurn transcripts on user-account deletion, key rotation, or a GDPR/data-export request. ResumeProfile.factsJson and MockTurn.transcript hold PII that flows into prompts; the design's target schema asserts 'every owned row userId + onDelete Cascade' as a principle but never verifies the moat tables actually have it, nor addresses transcript retention for a custody product. No deletion/retention test class is proposed.

- OUTCOME-CAPTURE FUNNEL (the #1 moat event per the founder's own memory) is named only abstractly: the design says 'drive A1 outcome capture against real users' in Phase 2 but never inspects the actual outcome/route.ts capture mechanism, who triggers it, when (self-report? employer?), or its abandonment/selection-bias risk. The single most strategically important event in the product gets one roadmap bullet with no design analysis of HOW a real hire/no-hire label is obtained — which is the entire defensibility thesis. This is the biggest content gap relative to the founder's stated goal.

- CONCURRENCY / MULTI-TAB on the single-writer turn-queue: the FSM and turn-queue assume one writer per session, but nothing prevents a user opening the same LIVE session in two tabs (or the rehydrate path racing the original). The design's D5 rehydrate adds a second client that mints an ephemeral and enqueues against the same seq space; the only guard is @@unique([sessionId,seq]) producing SEQ_CONFLICT. The interaction between rehydrate (D5) and a still-live original tab is never analyzed — a real way the proposed fix could double-bill or interleave turns.

- PROMPT-INJECTION / TRUST BOUNDARY on resume-grounded instructions: resume-digest.ts:17 hard-casts factsJson (as unknown as ResumeFacts) with NO runtime validation and feeds it straight into buildInterviewerInstructions at mint time. The architecture audit flags the missing write-time schema, but the design's response is only 'add resumeFactsSchema' — it never treats the resume text as an injection vector (a candidate could embed instructions in a resume bullet that the seat persona then ingests). For a product that injects user-controlled text into a system prompt, adversarial-resume handling is an unaddressed failure class.
